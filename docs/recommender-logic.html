ORIGIN Recommender — Logic Reference

ORIGIN Project Recommender Service v1 Internal — not for distribution

This document describes the recommendation logic as a decision procedure. It is intended for clinical and research colleagues who need to understand what the system does without reading code, and as a basis for a methods section in future publications. Tunable parameters are listed in §8 with their current values and rationale.

Terminology. A connectedness score is the participant's answer to the first question after reading a story (1–5 scale). A batch is the set of 6 stories returned to the app. A participant is cold-start until they have scored at least one story.

1. Top-level decision procedure

Every time the app requests recommendations, the engine runs the following procedure:

get_recommendations(participant)
IF participant has no scored stories yet:
    RETURN cold_start(participant)              → see §2

IF no new score since last visit
AND no abort event since last visit
AND preserved_visit_count < MAX_PRESERVED_VISITS (3):
    preserved ← last batch, minus stories opened-but-not-scored
    IF preserved contains 6 stories:
        preserved_visit_count ← preserved_visit_count + 1
        RETURN preserved                         → see §3

── new score arrived, abort fired, or stale batch ──
preserved_visit_count ← 0
RETURN fresh_recommendations(participant)   → see §4

2. Cold start

When a participant has no engagement history, personal preference cannot be inferred. The batch is built from the most recently added stories and the most popular stories among others in the same participant group.

cold_start(participant)
group ← all participants of the same type
         (trial / test / usability — groups are isolated from each other)

slot 1  — topical:
    take the most recently added story not yet seen by this participant

slots 2–5 — popularity:
    rank all catalogue stories by mean connectedness across group
    IF COLD_START_SEED is configured:
        blend seeded story weights into this ranking              → see §8
    sample 4 at random from the top COLD_START_POPULAR_POOL_SIZE (12)
    (random draw prevents one story being shown to every new user)

slot 6  — wildcard:
    pick one unseen story at random from the catalogue

RETURN [slot 1, slots 2–5, slot 6]

3. Batch preservation

If a participant opens the app between sessions without having scored a story, the same batch is returned with their place held. This is the intended behaviour for a participant who was interrupted mid-session.

To prevent a participant who rarely scores from seeing the same six stories indefinitely, the preserved batch is treated as stale after MAX_PRESERVED_VISITS consecutive unscored visits, and a fresh batch is generated on the next request.

An abort event ("Get me out of here") always bypasses preservation regardless of the visit count — it is a deliberate signal that the participant wants different content, distinct from an accidental early exit.

4. Fresh recommendations

Each batch of 6 is filled from four strategies. The default slot allocation is:

Content-based
2
Matched to participant's tag-affinity profile
Collaborative
2
Liked by participants with similar taste
Topical
1
New to this participant since last visit
Wildcard
1
Random unseen story
fresh_recommendations(participant)
seen               ← stories participant has scored
recently_recommended ← stories in last RECENT_BATCHES_TO_EXCLUDE (2) batches
excluded           ← seen ∪ recently_recommended

slot_counts ← {content-based: 2, collaborative: 2, topical: 1, wildcard: 1}

IF participant is highly engaged:                        → see §6
    slot_counts[content-based] ← 1
    slot_counts[wildcard]      ← 2
    (widens exploration as the preference profile matures)

FOR EACH slot_type in slot_counts:
    fill from strategy(participant, excluded)             → see §5
    add filled stories to excluded

IF fewer than 6 stories found:
    top up from content-based / topical / wildcard,
      still excluding seen but relaxing recent-batch window
    (early trial: collaborative underproduces until overlap builds)

apply re-engagement ramp(participant, batch)             → see §7

ensure at least MIN_FRESH_PER_BATCH (2) stories in this batch
  have never been recommended to this participant before

RETURN batch of 6

5. Recommendation strategies

Content-based

content_based(participant, excluded)
FOR EACH unseen story not in excluded:
    score ← weighted sum of tag_affinity[tag] for each tag on story
             (tag_affinity built from participant's scored history — see §6)

shuffle the top POOL_SIZE (6) candidates uniformly
(shuffling prevents a narrow positive-feedback loop where a small number
 of high-affinity stories are always returned first)

yield from shuffled pool

Collaborative

collaborative(participant, excluded)
FOR EACH other_participant in same group:
    similarity ← Pearson correlation of connectedness scores
                  on stories both have scored

recommend stories scored highly by similar participants
  that this participant has not seen,
  ranked by similarity-weighted connectedness
Early-trial behaviour. Collaborative filtering requires at least two participants to have scored the same stories. It will underperform in the first few weeks of the trial and gradually improve as engagement data accumulates. This is expected and is handled by the top-up logic in §4.

Topical

topical(participant, excluded)
Three-tier selection — first non-empty tier wins:

IF BOOSTED_STORY_IDS is configured:
    yield those stories (editorial curation)               → see §8
    RETURN

recent ← stories with created_at > now − TOPICAL_NEW_STORY_DAYS
         and not in excluded
IF recent is non-empty:
    yield recent in random order                           (auto-surfaces new content)
    RETURN

Fallback — catalogue is frozen or nothing new:
yield all unseen stories in random order                   (behaves like a second wildcard)

During a trial with no new stories published, topical always reaches
the fallback — giving uniform cold-start coverage with no recency bias.

Wildcard

wildcard(participant, excluded)
yield one unseen story chosen uniformly at random
  from all catalogue stories not in excluded

6. Preference profile

Each participant's preference profile is a dictionary mapping story tags to affinity weights (0–1). It is recomputed after each scored engagement, using all entries in the participant's history up to MAX_HISTORY_SIZE. Older scores contribute less via exponential decay with a 14-day half-life.

build_tag_affinity(participant)
FOR EACH story s the participant has scored:
    age_weight(s) ← exp(−days_since_scored(s) / 14)
    FOR EACH tag t on story s:
        weighted_sum[t]   += age_weight(s) × connectedness(s)
        weight_total[t]   += age_weight(s)

FOR EACH tag t:
    tag_affinity[t] ← weighted_sum[t] / weight_total[t]

── high-engagement check ──
scored_rounds ← number of stories participant has scored

participant is highly engaged IF:
    scored_rounds ≥ HIGH_ENGAGEMENT_MIN_ROUNDS (5)
    AND mean connectedness ≥ HIGH_ENGAGEMENT_SCORE_THRESHOLD (4/5)

── note on high-baseline raters ──
A participant who scores consistently high may reflect genuine connection
or an individual tendency to rate positively (self-reporting artefact).
From the recommender's perspective both are equivalent: a flat high-scoring
profile gives the content-based model little to discriminate on. Widening
exploration is therefore appropriate in either case — increasing variety
rather than reinforcing a weakly-informed preference signal.

7. Re-engagement ramp

When a participant is nearing catalogue exhaustion (fewer than 18 unseen stories), previously scored high-connectedness stories are gradually blended back in. The ramp reaches full re-engagement when no unseen stories remain.

re_engagement_ramp(participant, batch)
unread ← |catalogue| − |stories participant has scored|

IF unread ≥ REENGAGEMENT_RAMP_THRESHOLD (18):
    RETURN batch unchanged

ramp_fraction ← 1 − unread / REENGAGEMENT_RAMP_THRESHOLD
n_slots       ← ceil(6 × ramp_fraction), minimum 1

pool ← participant's scored stories, ranked by connectedness (highest first),
       excluding stories already in this batch

FOR i in 1 .. n_slots:
    drop the lowest-priority story from batch
    add top story from pool not already in batch

RETURN modified batch

8. Parameters

All named constants are set in engine.py and require a code deployment and service restart to change. Environment variables (COLD_START_SEED, BOOSTED_STORY_IDS) can be changed via deployment configuration without a code change.

Parameter Value Rationale
MAX_PRESERVED_VISITS 3 Maximum unscored visits before the preserved batch expires and a fresh set is generated. Prevents a low-engagement participant from seeing the same 6 stories indefinitely.
COLD_START_POPULAR_POOL_SIZE 12 Cold-start popularity slots sample at random from this many top-ranked stories. Prevents one story from being shown to every new participant.
REENGAGEMENT_RAMP_THRESHOLD 18 Re-engagement begins when fewer than this many unseen stories remain (3× a single batch). Calibrated at ~9% of a 200-story catalogue.
MIN_FRESH_PER_BATCH 2 Minimum number of stories in each batch that have never been recommended to this participant before. Ensures ongoing variety even as re-engagement ramps up.
RECENT_BATCHES_TO_EXCLUDE 2 Stories from the last N batches are excluded from fresh recommendations to prevent short-term cycling. Relaxes automatically when the catalogue is too small to honour it.
MAX_HISTORY_SIZE 70 Maximum scored stories retained per participant (≈35% of a 200-story catalogue). Oldest entries are evicted first; tag affinity is recomputed from survivors. Should be set to 30–40% of the actual launch catalogue size.
HIGH_ENGAGEMENT_MIN_ROUNDS 5 Minimum scored rounds before exploration widening can activate. Configurable via env var — set before trial launch; logged on startup.
HIGH_ENGAGEMENT_SCORE_THRESHOLD 4/5 Mean connectedness threshold for exploration widening. When scores are consistently at or above this level — whether from genuine connection or from an individual tendency to rate positively — the content-based affinity profile becomes less discriminating. Widening into an extra exploration slot is therefore appropriate in either case. Configurable via env var — set before trial launch; logged on startup.
POOL_SIZE 6 Content-based candidates are scored by affinity match and the top N are shuffled before selection. Smaller = faster personalisation; larger = more variety.
COLD_START_SEED env var Optional: story_id:weight, ... — editorial story list (0–1 weights) blended into the cold-start popularity ranking. Each entry contributes one synthetic vote; real trial engagement progressively outweighs it.
BOOSTED_STORY_IDS env var Optional: story_id, ... — stories promoted into the topical slot as tier 1 (wins over new and random). Used to curate the new-user experience or promote seasonal content.
TOPICAL_NEW_STORY_DAYS 30 Stories published within this many days are auto-surfaced as tier 2 of the topical slot. Set to 0 to disable and always use the random fallback. During a trial with a frozen catalogue this tier never fires.
